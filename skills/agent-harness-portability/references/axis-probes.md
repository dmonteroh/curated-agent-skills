# Axis probes

One entry per axis in the disposition table. Each carries the probe question to answer per target, how a `verified` answer is obtained, the silent failure the axis produces when it is wrong, and the repair move that closes it. Nothing here names a product: every value is a per-target lookup with an expiry date, and the values in the source this was recovered from were one team's undated assertions about third-party agents.

A cell reads `verified` only when the probe was answered against the target itself — its own documentation or its observed behavior. A cell reads `default — checked` when the probe was answered and the answer matched the assumed default. A cell reads `unknown` in every other case, including "the default is probably fine".

## 1. Invocation name

- **Probe:** what command starts this agent, and does that string differ from the agent's own name?
- **Verify:** the target's install documentation, or the resolved executable on a machine that has it.
- **Silent failure:** detection logic keyed on the agent's name matches nothing, and the target is skipped without an error — the corpus reports success having installed nowhere.
- **Repair:** record the command and its aliases as data, never as a name derived from the target's label.

## 2. User-scope root

- **Probe:** where does this agent look for user-level items?
- **Verify:** the target's own documentation for user-scope installation.
- **Silent failure:** the tree lands beside the location the agent reads, so nothing loads and nothing errors.
- **Repair:** rewrite the path per target.

## 3. Project-scope root

- **Probe:** where does this agent look for repository-level items, answered independently of axis 2?
- **Verify:** the target's own documentation for project-scope installation. Answering by deleting a leading home-directory reference from the user-scope root is a derivation, not a verification.
- **Silent failure:** project-scope items load for some targets and not others, which reads as a flaky corpus rather than a path defect.
- **Repair:** resolve and record two paths per target. Targets do diverge here — a user-scope root under a configuration directory alongside a project-scope root under a plain dot-directory is a real observed shape, as is a target whose two roots sit under different dot-directories entirely.

## 4. Subdirectory prefix

- **Probe:** which dot-directory does this target hang its other files off?
- **Verify:** the target's documentation, plus the two roots above — the prefix is frequently, but not always, their common parent.
- **Silent failure:** companion assets and manifests land outside the tree the agent scans.
- **Repair:** record the prefix as its own value rather than deriving it from either root.

## 5. Root indirection

- **Probe:** are this target's roots literal paths, or resolved at run time through an environment variable?
- **Verify:** the target's documentation. Where indirection exists, also record what the variable resolves to when unset.
- **Silent failure:** a literal path is written into content that the target resolves relative to a variable, so the reference points at a location that exists on the authoring machine and nowhere else.
- **Repair:** rewrite the path per target, and treat "the target declares indirection" and "the corpus contains a resolved path" as two separate cells — a target can declare indirection that no content in the corpus actually exercises.

## 6. Frontmatter dialect

- **Probe:** which keys does this target permit, does it filter by allowlist or denylist, does it rename any key, does it inject any key, does it cap the description, and what does it do on overflow?
- **Verify:** the target's own schema or loader documentation. Six sub-answers; a single "frontmatter is fine" answers none of them.
- **Silent failure:** two shapes. An unlisted key is dropped without a message, and a description over the cap is truncated so the target's selector no longer matches the item — the item appears to simply never trigger.
- **Repair:** re-express or inject the key per target; choose the overflow behavior deliberately. Two constraints from the skill file apply here and are the ones most often violated: any injected key must also appear in that target's allowlist, and every security-relevant key needs an explicit per-target disposition rather than being dropped by omission.

## 7. Sidecar manifest

- **Probe:** does this target require a machine-readable index emitted alongside the corpus, and in what format?
- **Verify:** the target's documentation. Where the format is generated by a tool rather than specified, record that the format is unspecified rather than guessing at it.
- **Silent failure:** the corpus installs correctly and the target lists none of it, because the target enumerates from the manifest rather than the tree.
- **Repair:** emit the manifest per target as a build output.

## 8. Item exclusions

- **Probe:** which items in the corpus are meaningless, recursive, or self-referential on this target?
- **Verify:** read the corpus, not the target. Any item whose subject is an agent is a candidate for exclusion on that agent.
- **Silent failure:** an item that delegates to agent X ships to agent X, where it either no-ops or spawns a copy of the caller.
- **Repair:** exclude per target. Note the asymmetry: a wrapper item that drives agent X *from* agent Y is a legitimate item on Y and an exclusion only on X, so exclusion lists are not symmetric and cannot be generated from the item's name alone.

## 9. Path rewrites

- **Probe:** which literal path strings appear in the corpus body, and what does each become on this target?
- **Verify:** grep the corpus for every path root in the token list, including the roots of other targets.
- **Silent failure:** two. A shortest-first ordering lets a general entry consume the prefix of a specific one, so a special-cased sub-path lands in the wrong place. And a rewrite list covering only the source agent's paths leaves every cross-agent example in the prose pointing at a foreign tree.
- **Repair:** rewrite the path, ordered longest-prefix-first, over a token list built from the corpus rather than from the source agent alone.

## 10. Tool vocabulary

- **Probe:** what is each tool called on this target, and which source tools have no equivalent at all?
- **Verify:** the target's tool documentation, one source tool at a time. An empty vocabulary is an answer only when it was checked — it is otherwise the most common form of `unknown` in a portability matrix.
- **Silent failure:** the shipped instruction names a tool the target does not have. Nothing errors; the agent improvises or stalls. This is the axis where an unfilled entry is most costly, because the corpus reads as configured.
- **Repair:** the ladder in the skill file — rename, collapse, capability prose, intent prose. Coverage is checked per tool name and per phrasing, never per table: a vocabulary listing four of seven tools, or one of three phrasings, presents as complete.

## 11. Capability sections

- **Probe:** what does the corpus instruct that this target structurally cannot do?
- **Verify:** map each capability-bearing section to the target's feature set. Capabilities worth checking first are the ones that invoke a second model, that depend on a specific backend service, and that require persistent state between sessions.
- **Silent failure:** the target reads an instruction for something it cannot do and substitutes something else.
- **Repair:** suppress the section, or leave it in when it already degrades gracefully at run time — the decision point in the skill file. Whichever is chosen, state the reason at the suppression site, because a suppression with no recorded reason cannot be re-evaluated when the target gains the capability.

## 12. Companion assets

- **Probe:** which non-instruction files does the corpus depend on, and does this target's installation carry them?
- **Verify:** grep the corpus for references to files outside itself.
- **Silent failure:** instructions reference a helper or template that was never installed, so every run that reaches it fails at that step only.
- **Repair:** install the assets alongside the corpus, or remove the dependency.

## 13. Materialization

- **Probe:** is the target's tree copied, linked, or generated, and is it checked in or a build artifact?
- **Verify:** the corpus's own installation mechanism, per target.
- **Silent failure:** a generated tree is edited in place, and the next build discards the edit.
- **Repair:** treat generated trees as build artifacts — ignored by version control, regenerated before checks, with a freshness check that fails on a stale tree.

## 14. Cross-agent boundary

- **Probe:** does this target share a checkout with another agent's tree, and what does it do when it reads that tree?
- **Verify:** whether both trees can be present at once in a working copy.
- **Silent failure:** a foreign agent reads another agent's instruction tree as ordinary repository content and follows prompt templates never addressed to it.
- **Repair:** a boundary instruction, ranked as the weakest available control and paired with a real one — not installing both trees, or scoping the foreign agent's read root. The ranking is authored, not sourced.
