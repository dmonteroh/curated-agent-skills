# Network Change Review

Provides a layered pre-deploy gate for a network configuration that has not been applied yet. The layers run in a fixed order that puts irreversibility first, and the gate is explicit: some findings fail the change closed, others warn without blocking. The review is a warning layer, not a device-accurate parser — final approval still needs an engineer who has confirmed platform, intent, and rollback.

## Use this skill when

- A router or switch configuration is about to be pushed, by hand or by an automation run
- Config generated by a script, template, or model needs a pre-flight check before it reaches production
- A change window needs its rollback path and out-of-band access confirmed before it opens
- An ACL, route-map, or prefix-list change needs review for direction, mask form, and dangling references
- A pre-flight gate is being built into a network automation pipeline

## Do not use this skill when

- The device is already misbehaving and the need is evidence about live state, not review of a candidate artifact
- The configuration is a cloud VPC, route table, security group, or peering — cloud network design owns that, and none of the syntax layers here apply
- The change is a Kubernetes NetworkPolicy, service mesh route, or container network plugin — that is cluster networking, a different artifact and a different blast radius
- A device-accurate parse is what is actually needed; this review warns on patterns and will both miss and over-report against a real parser
- The question is which design to adopt rather than whether this artifact is safe to apply

## Required inputs

- The exact candidate configuration, as it will be applied — not the template it came from
- The current running configuration of the target device, or a stated acknowledgement that it was unavailable
- The change window, the rollback command set, and how out-of-band access is reached

## Workflow

Run the layers in order. Order is the point: a destructive command found at layer 1 makes layers 3 through 5 irrelevant, and finding it last means the review spent its attention on banner text.

1. **Destructive commands.** Anything that reloads, erases, formats, removes a routing process, removes interface configuration, changes authentication behaviour, or rotates device keys.
   - Gate: **fail closed.** No destructive command proceeds on a pre-flight pass; it needs its own named approval.
2. **Credential and management-plane exposure.** Plaintext credentials, weak or default community strings, superseded protocol versions, VTY blocks reachable from anywhere, missing session timeouts.
   - Gate: **fail closed.**
3. **Address collisions.** Duplicate addresses and overlapping subnets across the candidate, evaluated against the interfaces the config actually defines.
   - Gate: **fail closed** on a duplicate address; overlaps are fail-closed unless the design deliberately overlaps and says so.
4. **Stale references.** ACLs, route-maps, prefix-lists, class-maps, and interfaces that are referenced but never defined — including references the candidate inherits from a running config it will replace.
   - Gate: **fail closed.** A dangling filter reference is a silently permissive device.
5. **Operational hygiene.** Time sync, log timestamps, a remote logging destination, login banners, SNMPv3 where v2c is present.
   - Gate: **warn, do not block**, when the gap is outside the change's scope. Blocking an interface description change on a missing NTP server trains people to skip the gate.

Then, before the window opens:

6. **Confirm the change cannot sever management access.** Name the out-of-band path and confirm it is reachable now, not in principle. A management-plane change without a proven console path is the one failure this review cannot warn its way out of.
   - Decision: if no out-of-band path is confirmed, the management-plane portion does not proceed regardless of how clean the layers came back.
7. **Diff the candidate against the device, not against the template it came from.** Templates drift from what is actually running; the device is the only authority on the starting state.
   - Output: the applied diff, reviewed line by line.
8. **Apply the smallest increment inside the window, re-read state, and compare against the baseline captured before the change.**
   - Decision: if post-change checks fail, roll back — do not persist and investigate afterwards.
9. **Persist only after post-change checks pass.** On a two-stage device, the active configuration and the one that survives a reload are different objects. Saving because a command was accepted converts a bad change into a bad reboot, and it is the single most common way a reviewed change becomes an outage hours later.

## Decision points

- **A finding at layers 1–4 fails the change closed.** A finding at layer 5 warns. If a layer-5 gap is inside the change's own scope, it is promoted to a blocker — the change is already touching that surface.
- **Wildcard masks are not subnet masks.** IOS-style ACLs and several routing statements take the complement. `255.255.255.0` written where `0.0.0.255` belongs matches a far wider range than intended, and it is the most common error in generated network config because the subnet form is what the surrounding text uses. Check every mask in an ACL or `network` statement against `references/ios-syntax.md`.
- **Every ACL ends in an implicit deny.** If the operational goal includes observing what was missed, add an explicit logged deny — after confirming the log volume is safe.
- **Never test whether a filter is the problem by removing the filter.** Read hit counters, logs, and route state. Removing it converts a scoped fault into an open device and destroys the evidence in the same step.

## ACL placement review

Before an ACL is bound to an interface, each of these has an answer or the binding does not proceed:

- Which direction is filtered, inbound or outbound, and does that match where the traffic actually enters?
- Is management traffic sourced from a known jump host or management subnet, and is it permitted?
- Is there an explicit permit for required routing, DNS, NTP, monitoring, and application traffic?
- Are hit counters readable from a planned test source — not a generic ping from wherever?
- Is there a rollback command and an active console or out-of-band path?

## Constraints

- Regex checks are a pre-flight warning layer. They will miss constructs a real parser catches and flag strings that are fine in context. Never report their output as a validation pass.
- Collect only the config sections under review. A full running config pasted into a ticket or an external tool carries secrets, customer names, and private topology.
- Findings carry a line number and a type. A finding without a location is not actionable inside a change window.

## Common pitfalls

- Applying generated config without a device-specific diff
- Saving configuration before post-change checks pass
- Using a subnet mask where a wildcard mask is expected
- Binding an ACL to the wrong interface direction
- Treating a template as the baseline instead of the running config
- Recommending SNMPv2 community strings as a monitoring requirement

## Output contract

- Verdict: **blocked** or **cleared to proceed**, stated first
- Blocking findings, each with its layer, line number, matched text, and why it blocks
- Warnings, each with its layer and line number, and whether it falls inside the change's scope
- The rollback command set and the confirmed out-of-band path
- What was not checked, and why — platform constructs the pattern layer does not cover belong here explicitly

## Examples

**Blocked at layer 2.** A generated VTY block ships `transport input telnet ssh` and no `access-class`. Verdict: blocked. Two findings, both layer 2, with line numbers. The interface changes in the same candidate are clean but do not proceed separately — the management plane is in scope for this change, so the layer-5 timeout gap is promoted to a blocker alongside them.

**Cleared with warnings.** An interface description and trunk VLAN list change. Layers 1–4 clean. Layer 5 reports no remote logging destination. Verdict: cleared to proceed, one warning, outside scope. Rollback is the prior three lines; out-of-band is the console server, reachability confirmed at review time.
