## 2. Defects found in existing measurement material while building this

These are reported, not fixed: the files are outside this build's scope.

- **Codex arms were never bare** (fact). `tmp/writing-style-skill/measure/lib/vendor.sh` copies `~/.codex/config.toml` into every arm home. That file carries `[mcp_servers.laya-mcp]` and trusted-project entries. Every Codex arm since the laya server was added saw an extra MCP tool. `skill_eval.vendors.build_home` generates the config instead.
- **The laya "bare" arm carried a skill** (fact). `tmp/laya-mcp-skill/measure/homes/claude/bare/skills/synced/…/skill-creator` exists, so that arm's "no skill" condition had `skill-creator` installed. The claude.ai skill sync below explains how it got there: the CLI wrote it into the reused home mid-run.
- **Built-in skills compete in every Claude arm** (fact). The init event of a bare home with one skill installed listed 18 to 20 built-ins beside it (the count changed during the session). One built-in is named `code-review`, the same as a library skill. No earlier harness recorded which skills were visible. `activation` now checks the init list against the expected set and the built-in baseline, and marks mismatched records as contaminated.
- **Arms inherited the orchestrator's session** (fact, R1). Arms spawned with the parent's environment carried `CLAUDE_CODE_MESSAGING_TOKEN` and a `HOME` pointing at the real home, and their init events listed `SendMessage` and `ListAgents`. Any harness that spawns `claude -p` from inside a Claude Code session with the default environment has this defect. The old `tmp/` harnesses pass the environment through unchanged (fact, `measure/lib/vendor.sh`). Whether they were launched from inside a session is inference, but most of their runs were dispatched by agents.
- **claude.ai skill sync leaks org skills into bare homes** (fact, R2, claude 2.1.280). The CLI downloads account-provisioned skills (`anthropic-skills:*`, including `anthropic-skills:writing-style`) into `<config dir>/skills/synced/` during a run. It did so in 3 of 6 control runs, and a home reused across calls then shows them. `--strict-mcp-config` does not stop it, `--bare` loses authentication, and no environment variable turns it off. `--settings '{"syncClaudeAiSkills":false,"syncClaudeAiPlugins":false}'` stopped it in 16 of 16 runs. Every earlier Claude activation or benchmark measurement in this repository ran without that guard.
- **A denylist does not remove Claude tools reliably** (fact, R2). `--disallowedTools` prints no warning for an unknown name, so a typo fails open. Arms now get the `--tools` whitelist.

## 3. Suggested order (inference)

1. R7 and R4 first. They are static and free, and they tell the operator how much of the corpus is measurable before any money is spent.
2. Fix the corpus for a handful of skills (the four installed into other projects: `prompt-engineering`, `smart-conventional-commits`, `shell-scripting`, `pr-description`), then run R1 on both vendors.
3. R2 on known collision pairs.
4. R3 once the review runner is next opened for other work. It retires the one gate the operator has already ruled against.
5. R5 and R6 together, since both are dispatch-scope changes to the same prompts.
